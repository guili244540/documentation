## 4. Technical approach

- **Upload inside an activity** (determinism rule C4): `publish-testlog-file` runs in the worker process with `FILES_API_KEY` (the worker's SA token cannot call `/v1/files` — verified live 2026-11-21); the workflow only passes the bytes/blob sha through `SheetState`. No env reads in workflow bodies.
- **Client:** `FILES_API_KEY` when bound (workspace key, read inside the activity; new `mistral_client_with_api_key` helper in `utils.mistral`), else the app credential. Both target `env.mistral_base_url` / the public API — the Files API lives on the main Mistral API host, not `WORKFLOWS_BASE_URL`. Tests monkeypatch the `_files_client` seam, so no network.
- **Dedup/cleanup:** in-process `dict[blob_sha, PublishedFile]`; on a new blob sha, upload then delete the previous file id (best-effort, logged on failure). On a cache hit the activity first checks the file still exists (`files.retrieve_async`): a 404 (e.g. a manual deletion outside the worker) evicts the id from cache/registry/tracker (`_forget_published_file`) and re-uploads; any other error keeps the cached reference; the signed URL is re-minted on every hit so a returned link always has the full TTL. No `expiry` on upload (accepted range unverified live) — retention is enforced by the purge cron below, which also reconciles the cache (and treats a 404 delete as already gone), so a cached `file_id` whose file was deleted is re-uploaded rather than returned stale.
- **Signed URL:** after a successful upload, mint `client.files.get_signed_url_async(file_id=..., expiry=1)` (SDK TTL is in hours, valid range 1–168 → shortest is 1 h; `SIGNED_URL_EXPIRY_HOURS = 1`) and return it as `signed_url` (`""` on mint failure — the `file_id` still stands). The effective link lifetime is bounded to ≤ 10 min by the purge, so the 1 h signature TTL never extends real access. Never place a token in the URL (C10).
- **Retention purge:** `publish-testlog-file` registers `file_id → created_at` (`_now()`, a monkeypatchable seam) in the **process-local** `_published_registry` (same pattern as the blob-sha cache). The `purge-testlog-files` workflow (schedule `*/5 * * * *`, created via the schedules API at deploy time) runs the `purge-old-testlog-files` activity, which deletes registry entries older than `PURGE_MAX_AGE` (5 min) via `client.files.delete_async` and removes them from the registry. **Only registered ids are ever deleted; `files.list` is not used for deletion** (a name match cannot prove ownership). Best-effort, logged on failure (error class + status, never the key); a file lives at most ~10 min. Accepted limitation (owner decision 2026-11-21): the registry is process-local — after a restart (or when the cron lands on another replica) it is empty, so the previous upload is orphaned until manual deletion; no registry file is written to the GitHub repo. Purge calls are Mistral API calls and stay outside `GITHUB_API_RATE_LIMIT`; no GitHub calls are added. The purge also reconciles the blob-sha cache, so a cached `file_id` whose file was deleted is re-uploaded rather than returned stale.
- **Failure semantics:** any upload/mint error → `file_id = ""` / `signed_url = ""` and a warning log line (never the token/key); the inline artifact path keeps working (R5/C8).
- **Security:** `file_id` is not a capability — download requires the caller's own token at `/v1/files/{id}/content` (C10/R2); the signed URL is the single time-bounded exception (≤ 10 min effective). `GITHUB_TOKEN` untouched (C2).

## 7. Rollout and rollback

- Fully additive: new optional `file_id` output field only; inline behavior unchanged (C8).
- Rollback: revert the branch commit(s), or delete the uploaded files; the worker change is backward compatible on its own. Revoking a signed URL = deleting its file — the purge does that within ≤ 10 min anyway, so there is no separate URL revocation.
- Size guard (C6): inline base64 ≤ 1 MB (GitHub) / 2 MB (payload); Files API cap 512 MB. Current file ~30 KB.
